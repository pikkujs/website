# Advanced configuration

Most projects never touch these. Reach for one when a default gets in your way. The options you do need are in [Configuration](/docs/pikku-cli/configuration).

## Scaffold

The `scaffold` section controls where `pikku new` puts generated files and which features are enabled.

```json
{
  "scaffold": {
    "pikkuDir": "src/pikku",
    "functionDir": "src/functions",
    "wiringDir": "src/wirings",
    "middlewareDir": "src/middleware",
    "permissionDir": "src/permissions",
    "addonDir": "packages/addons",
    "rpc": true,
    "agent": true,
    "workflow": true
  }
}
```

<div data-code-ink="">

```text
Scaffold:

  pikkuDir <string>
      Directory for auto-generated scaffold files — RPC endpoints, agent
      endpoints, workflow routes, the Better Auth wiring (default:
      <srcDirectories[0]>/scaffold, resolved against rootDir)
  functionDir <string>
      Where pikku new function puts files (default:
      <srcDirectories[0]>/functions)
  wiringDir <string>
      Where pikku new wiring puts files (default: <srcDirectories[0]>/wirings)
  middlewareDir <string>
      Where pikku new middleware puts files (default:
      <srcDirectories[0]>/middleware)
  permissionDir <string>
      Where pikku new permission puts files (default:
      <srcDirectories[0]>/permissions)
  addonDir <string>
      Base directory for pikku new addon; the package is created at
      <addonDir>/addon-<name> (default: current working directory)
```

</div>

### Feature flags

Feature flags are the keys that switch a generated surface on. Set them with `pikku enable <feature>` or by hand. (`pikku enable` also writes `scaffold.pikkuDir: "pikku"` if you haven't set one.)

Each flag says only whether the *surface exists* and where its file goes. It never says who may call the surface: authentication is declared on the function, its wiring, its scopes and its addon, and enforced there on every call.

| Value | Meaning |
|---|---|
| `true` | the surface exists, at its default path under `pikkuDir` |
| `{ "path": "src/my.gen.ts" }` | the surface exists and is written to `path` instead (relative to `rootDir`, or absolute) |
| `false` or absent | the surface is not generated |

Only `path` is accepted as an object key. A bare string, an unknown key, and the old `auth` key are all refused when the config loads, with a message saying so. `graph` and `webhook` are plain booleans: no `path` override.

| Flag | Generates | Default path (under `pikkuDir`) | `pikku enable` |
|---|---|---|---|
| `rpc` | `POST /rpc/:rpcName` | `rpc/rpc-public.gen.ts` | `rpc` |
| `agent` | Agent HTTP endpoints | `agent/agent.gen.ts` | `agent` |
| `workflow` | Workflow HTTP routes | `workflow/workflow-routes.gen.ts` | `workflow` |
| `events` | `/events` WebSocket channel + `/events/:topic` SSE | `realtime/events.gen.ts` | `events` |
| `meshRpc` | Mesh RPC worker + `POST /mesh/rpc/:rpcName` | `rpc/rpc-mesh.gen.ts` | `mesh-rpc` |
| `remoteJobs` | Job inbox routes for queue and scheduled work | `remote-jobs/remote-jobs.gen.ts` | `remote-jobs` |
| `webhook` | Outgoing webhook delivery queue worker | `webhook/webhook.gen.ts` | `webhook` |
| `analytics` | `POST /analytics` ingest | `analytics/analytics.gen.ts` | none (set by hand) |
| `featureFlags` | `GET /feature-flags` | `feature-flags/feature-flags.gen.ts` | none (set by hand) |
| `virtualUser` | Virtual-user run/read RPCs + run worker | `virtual-user/virtual-user.gen.ts` | none (set by hand) |
| `scenarios` | Scenario instrumentation in `pikku dev` / `pikku serve` (no file) | none | `scenarios` |
| `graph` | The `@pikku/addon-graph` wiring | `graph/graph.wirings.gen.ts` | none (set by hand) |

Every generated file is marked `.gen.ts`, is rewritten on each `pikku` run, and is picked up by the inspector like any other source file, so edit the source declarations rather than the output. When a flag is off, nothing is generated for it and any copy left at the old default path is not a source of truth.

#### `rpc`

Wires `POST <globalHTTPPrefix>/rpc/:rpcName` (with `auth: false` on the wire itself) so a client can call any function you've exposed over RPC. It does not expose anything new: a function is only reachable if it's marked `expose: true`, and its own auth rules still run. Turn it on when a browser or another service calls functions by name through the generated RPC client. Schemas go to `rpc-public.schemas.gen.ts` beside it. Off: there is no generic `/rpc` endpoint; the RPC client has nothing to talk to.

#### `agent`

Wires the public agent endpoints: `/rpc/agent/:agentName`, `/rpc/agent/:agentName/stream`, `/rpc/agent/:agentName/approve` and `/rpc/agent/:agentName/resume` (all under `globalHTTPPrefix`). Turn it on when you have AI agents and want to run them over HTTP. Off: agents still exist and can be called in-process, but have no HTTP surface.

#### `workflow`

Wires the workflow routes: `/workflow/:workflowName/start`, `/run`, `/approve/:runId`, `/status/:runId`, plus `/status/:runId/stream` and `/stream/full` for live status over a channel. Turn it on to start workflows and watch them from outside the backend. Off: workflows run from code only (via the workflow service); there is no HTTP way in.

#### `events`

Generates the realtime scaffold: a WebSocket channel at `/events` (clients subscribe and unsubscribe to topics) and an SSE route at `/events/:topic`. Both subscribe clients through the `eventHub` service, so provide one in your singleton services. When `clientFiles.fetchFile` is set and `clientFiles.realtimeFile` is not, the realtime client is written to `realtime.gen.ts` next to the fetch client. Off: no realtime channel; `pikku realtime` has nothing to point at.

#### `meshRpc`

Generates a queue worker named `pikku-mesh-rpc` and `POST /mesh/rpc/:rpcName`, both running functions marked `remote: true`. The HTTP side is guarded by pikku's remote-auth middleware rather than a user session. Turn it on when one pikku deployment calls another's internal functions. Since the worker is a queue worker, you need a queue service.

#### `remoteJobs`

Generates `POST /__pikku/queue-job` and `POST /__pikku/scheduler-job`, a job inbox for runtimes that have neither a queue consumer nor a clock (serverless, for instance). An external dispatcher posts a job, and pikku runs the matching queue worker or scheduled task. Both routes sit behind the `remoteJobsSecret` middleware from `@pikku/core/middleware`. Off: those runtimes can't be driven by an outside dispatcher.

#### `webhook`

Generates a queue worker named `pikku-outgoing-webhooks` that delivers outgoing webhooks using core's `pikkuWebhookWorkerFunc`. Boolean only. Turn it on when your app sends webhooks to customers. Since it's a queue worker, you need a queue service.

#### `analytics`

Generates `POST <globalHTTPPrefix>/analytics`, a typed ingest built from your `defineAnalyticsEvents` declarations. Codegen logs an error and skips the file if the project declares no events. The events metadata (`analytics/pikku-analytics-meta.gen.json`) is written whether or not this flag is on, so declaring events is useful on its own.

#### `featureFlags`

Generates `GET <globalHTTPPrefix>/feature-flags`, a read wire returning the flag state for the caller, from your `defineFeatureFlags` declaration (and `scopes/pikku-flags-manifest.gen.ts`). Codegen logs an error and skips the file if no flags are declared. Off: flags are still evaluated server-side; clients just can't read them over HTTP.

#### `virtualUser`

Generates the virtual-user surface: exposed RPCs to run a virtual user (`runVirtualUser`), read and list runs and their steps, and set schedules, plus a queue worker named `pikku-virtual-user-runs`. Requires at least one virtual user declared with `defineVirtualUsers`; with none, codegen fails with a message saying so. A scheduled tick (`tickVirtualUserSchedules`) is generated but deliberately not wired: pikku won't start spending model budget for you, so you add the `wireScheduler` yourself. The model comes from `scenarios.model`.

#### `scenarios`

Doesn't generate a file. When on, `pikku dev` and `pikku serve` register the scenario instrumentation (coverage reset/snapshot and service-call recording) that `pikku scenario run --coverage` relies on. It's registered at start-up rather than generated into the project, so a deployed bundle never contains it. Off: scenarios can still run against the server, but coverage endpoints aren't available.

#### `graph`

Wires the `@pikku/addon-graph` package (`wireAddon({ name: 'graph', package: '@pikku/addon-graph' })`) so `pikkuWorkflowGraph` can reference its native transforms such as `graph:editFields`. Boolean only. The package must be installed in your project.

## Models

`models` is an alias table so an agent can name a model by what it is for, and one edit repoints every use:

```json
{
  "models": {
    "cheap": "openai/gpt-5-mini",
    "reasoning": "anthropic/claude-sonnet-5"
  }
}
```

A `model` containing `/` is used as written; a bare name that is not in this table fails codegen. `pikku dev` and `pikku serve` accept `--model alias:provider/model` (comma-separated for several) to repoint aliases for one run without editing the config. Request-time overrides are passed as `input.model` when the agent runs. See [AI Agents](/docs/wiring/ai-agents) for details.

## Emails

```json
{
  "emailTemplatesDir": "src/emails"
}
```

Directory containing email templates, locales, partials, and `theme.json`. Used by `pikku emails init` / `pikku emails generate`. `pikku emails init` scaffolds a starter tree and writes this key for you.

## CLI Entrypoints

Configure CLI tools built with Pikku's CLI wiring.

```json
{
  "cli": {
    "entrypoints": {
      "my-cli": [
        { "type": "local", "path": "src/cli-local.ts" },
        {
          "type": "channel",
          "wirePath": "src/cli-channel.ts",
          "name": "cli",
          "route": "/cli"
        }
      ],
      "simple-cli": "src/simple-cli.ts"
    }
  }
}
```

Each entrypoint can be:
- A `string` — path to the wiring file
- `{ type: "local", path }` — direct command-line execution
- `{ type: "channel", wirePath, name?, route?, path? }` — remote execution via WebSocket
- An array of the above for multiple execution modes

## Deploy

Configure deployment providers and settings.

```json
{
  "deploy": {
    "providers": {
      "cloudflare": "@pikku/deploy-cloudflare",
      "aws": "@pikku/deploy-serverless"
    },
    "defaultProvider": "cloudflare",
    "serverlessIncompatible": ["heavy-compute-function"]
  }
}
```

<div data-code-ink="">

```text
Deploy:

  deploy.providers <Record<string, string>>
      Map of provider names to adapter packages (defaults: cloudflare →
      @pikku/deploy-cloudflare, serverless → @pikku/deploy-serverless, azure →
      @pikku/deploy-azure, standalone → @pikku/deploy-standalone)
  deploy.defaultProvider <string>
      Default provider for pikku deploy commands (default: cloudflare)
  deploy.serverlessIncompatible <string[]>
      Service names that can't run in serverless — any function that reaches
      one is routed to the server target
  deploy.defaultTarget <"serverless" | "server">
      Default deploy target for functions without an explicit deploy flag
      (default: serverless)
  deploy.grouping <object>
      How many deployment units the app's functions collapse into — {
      strategy: "services" | "function" | "single", rules: [{ unit, tags?,
      addon?, routes? }] } (services is the default). See Deployment unit
      grouping
  deploy.mangleIdentifiers <boolean>
      Rename identifiers when minifying worker bundles (default: true). Set
      false so a deployed worker's runtime errors name something you can
      search for
  deploy.bundler <"auto" | "bun" | "esbuild">
      Which bundler builds deployment units. auto (default) uses Bun.build
      under bun and esbuild otherwise; pin esbuild where bun's output
      misbehaves
  deploy.desktop <object>
      Desktop shell settings used by pikku deploy apply --desktop: {
      identifier?, url? }
```

</div>

## Addon Mode

When building a reusable addon package, set `addon` to enable addon-specific codegen.

```json
{
  "addon": true
}
```

Or with metadata for the addon registry:

```json
{
  "addon": {
    "displayName": "Slack Integration",
    "description": "Slack API functions for Pikku",
    "categories": ["Communication"],
    "icon": "slack-icon.svg",
    "serverlessIncompatible": ["streamLargeExport"],
    "openapi": { "version": "1.2.0", "hash": "abc123" }
  }
}
```

The addon object also accepts `serverlessIncompatible` (service names that must run on a server) and `openapi` (`version` + `hash`, stamped by `pikku new addon --openapi` to track the spec the addon was generated from). Two related top-level keys: `addonName` overrides the addon's package name in generated metadata (defaults to the `name` in `package.json`), and `addonMetaJsonFile` overrides where the addon metadata JSON is written (default: `{outDir}/console/pikku-addon-meta.gen.json`; the directory name is historical).

## Monorepo Support

```json
{
  "packageMappings": {
    "packages/sdk": "@my-app/sdk",
    "packages/functions": "@my-app/functions"
  }
}
```

Maps local directory paths to published package names so generated imports use the package name instead of relative paths.

## Filtering

Permanently filter which functions are included in codegen output. These are the config-file equivalent of the CLI `--tags`, `--wires`, etc. flags.

```json
{
  "filters": {
    "tags": ["api", "public"],
    "wires": ["http", "rpc"],
    "directories": ["src/api"]
  }
}
```

All `InspectorFilters` keys are supported: `names`, `tags`, `wires`,
`directories`, `httpRoutes`, `httpMethods`, every `exclude*` variant
(`excludeNames`, `excludeTags`, `excludeWires`, …), and `target` /
`excludeTarget` (`serverless` | `server`). Named presets can be defined under
`namedFilters` and selected with `pikku --filter <name>`.

## Linting

Configure lint rules. The first three are evaluated by codegen; the last by
[`pikku validate`](/docs/pikku-cli/commands/test#pikku-validate):

```json
{
  "lint": {
    "servicesNotDestructured": "warn",
    "wiresNotDestructured": "error",
    "functionDynamicImport": "warn",
    "customServerBootstrap": "error"
  }
}
```

| Rule | Values | Default | Description |
|------|--------|---------|-------------|
| `servicesNotDestructured` | `"off"` \| `"warn"` \| `"error"` | `"error"` | Warn when functions don't destructure services |
| `wiresNotDestructured` | `"off"` \| `"warn"` \| `"error"` | `"error"` | Warn when functions don't destructure wires |
| `functionDynamicImport` | `"off"` \| `"warn"` \| `"error"` | `"warn"` | Warn when a function body reaches for a dynamic `import()` |
| `customServerBootstrap` | `"off"` \| `"warn"` \| `"error"` | `"warn"` | Flag a `start`/`dev` script that boots a server without `pikku dev` or `pikku serve` |

### Frontends

`frontends` is the one list of the project's apps. `pikku app`, `pikku serve`,
`pikku deploy`, Fabric and native builds all read it.

```json
{
  "frontends": {
    "web": {
      "cwd": "apps/web",
      "primary": true,
      "kind": "spa",
      "dev": { "command": ["bun", "run", "dev"], "port": 7105, "healthPath": "/" },
      "serve": { "urlPrefix": "/", "spaFallback": true }
    },
    "admin": {
      "cwd": "apps/admin",
      "serves": "staff",
      "virtualUsers": ["manager"],
      "native": { "identifier": "com.acme.admin", "platforms": ["desktop", "android"] }
    }
  }
}
```

<div data-code-ink="">

```text
Frontends:

  cwd <string>
      Required. The frontend's project directory, where its package.json is,
      relative to the config file
  dist <string>
      Its build output, relative to cwd (default: dist). Pikku reads it and
      never builds it
  primary <boolean>
      The main app. Exactly one frontend should set it
  deploy <boolean>
      Whether Fabric deploys it
  kind <"spa" | "ssr" | "static">
      How it renders. An ssr frontend cannot be bundled into a native app
  dev <object>
      { command, port, healthPath } — how the dev runner starts it
  serves / virtualUsers <string / string[]>
      Who the app is for
  serve <object>
      Serve dist from the pikku server's own origin: { urlPrefix?,
      spaFallback? } (defaults / and true). At most one frontend may set it
  native <object>
      Package it as a desktop or mobile app. Written by pikku app native init
      — see Native Apps
```

</div>

#### `native`

<div data-code-ink="">

```text
native:

  native.identifier <string>
      Bundle id and Android package name. Unique across apps, fixed after the
      first store release
  native.productName <string>
      The name the OS shows (default: the app name)
  native.platforms <("desktop" | "android" | "ios")[]>
      Where it builds. At least one
  native.plugins <string[]>
      store, dialog, clipboard-manager, os, notification, geolocation,
      biometric, haptics, barcode-scanner, nfc
  native.url <string>
      Open a deployed origin instead of bundling dist. Cannot be combined with
      bundleServer
  native.bundleServer <boolean>
      Ship the compiled server as a sidecar. Desktop only; installed by pikku
      deploy apply --provider standalone --runtime bun
```

The project is written to `<cwd>/src-tauri`. See [Native Apps](/docs/deploy/native-apps).

`serve` names *output*, not a project: `pikku serve` and `pikku deploy` read
`dist` and never build it. `pikku dev` ignores it — a frontend dev server owns
that job and proxies API calls back to pikku, which is what keeps HMR working.

### Output File Overrides

Every generated file path is individually overridable at the top level of the config. By default they're all derived from `outDir` (e.g. `functionsFile`, `httpWiringsFile`, `schemaDirectory`, `bootstrapFile`, `virtualUsersWiringFile`, and several dozen more — one key per generated file listed in [Generated Files](/docs/pikku-cli/generated-files)). You rarely need these; the common exceptions are `authFile` (which lives in your source tree) and the `clientFiles` block above.

### Native Binary

Compile a TypeScript entrypoint to a self-contained native binary with
`pikku binary` (uses `bun build --compile`):

```json
{
  "binary": {
    "entrypoint": "src/start.ts",
    "output": "dist/server",
    "targets": ["bun-linux-x64", "bun-darwin-arm64"]
  }
}
```
