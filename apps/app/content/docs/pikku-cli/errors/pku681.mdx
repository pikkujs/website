# PKU681: Scenario Step Prose Names Its Virtual user

## Error Message

```
[PKU681] Scenario 'checkoutFlow' names its virtual user in the step prose: 'Shopper buys an apple' runs as 'shopper'. The reporter already renders the virtual user as the subject, so this reads "Given shopper Shopper buys an apple". Drop the name and let { virtual user: virtual users.shopper } supply it — the step reads as a bare third-person predicate.
```

## What Went Wrong

A step declares who it runs as via `{ virtualUser: virtualUsers.shopper }`, and its prose *also* opens with that virtual user's name — `'Shopper buys an apple'`, or `` `'shopper' buys an apple` ``.

The reporter composes each line as **phase + virtual user + prose**, so it already supplies the subject. Naming the virtual user again at the front of the prose doubles it up: the generated report reads "Given shopper Shopper buys an apple", and in a report where the virtual user is its own column or line prefix, the name is printed twice side by side. There's a correctness cost too — the hardcoded name silently desyncs the moment the call site switches virtual user, so a step you re-run as `virtualUsers.admin` still claims to be the shopper.

Only the **subject position** is refused. Naming someone mid-sentence ("sends shopper a receipt") is ordinary prose and passes, and a virtual user keyed after a role noun can still say "creates the admin client".

Pikku checks every string that could render for the step, in the runtime's own precedence: the call-site `description`, the step's `template`, the step definition's `description`, and the step name itself. So a clean step name won't save you if the `description` you passed opens with the virtual user.

## How to Fix

Delete the name from the front of the prose and let the `virtualUser:` option supply it. What's left should read as a bare third-person predicate — something that makes sense with "Given \<someone\>" glued in front of it.

The broken shape opens a step's prose with the virtual user's name, such as `'Shopper has an item in the cart'` or `` `'shopper' sees the order confirmed` `` while passing `{ virtualUser: virtualUsers.shopper }`.

Declare the virtual user once, in the option, and write the prose as a bare predicate (`'has an item in the cart'`, `'sees the order confirmed'`). See the scenario steps below for the shape.

Prose rewrites, before and after:

| ❌ Prose that trips PKU681 | ✅ Prose that renders cleanly |
| --- | --- |
| `'Shopper buys an apple'` | `'buys an apple'` |
| `` `'shopper' buys an apple` `` | `'buys an apple'` |
| `"shopper's cart is empty"` | `'has an empty cart'` |
| `'Susan opens the catalogue'` | `'opens the catalogue'` |
| `'admin approves the order'` | `'approves the order'` |

### If the offending string is the call-site description


If the offending string is the call-site `description` option, it overrides the step name and is what renders, so it is checked too. A `description: 'shopper buys an apple'` on `{ virtualUser: virtualUsers.shopper }` fails, while `description: 'buys a single apple'` passes.

### If the offending string is on the step definition


If the step definition's own `template` hardcodes the virtual user (for example `'shopper buys {qty} apples'`), it is wrong at every call site. Write `'buys {qty} apples'` instead and let the call site supply the virtual user.

### If you genuinely need two people in one line


A step run as `virtualUsers.admin` can say `'sends shopper a receipt'`. The subject is the virtualUser, and `shopper` is the object of the sentence.

## Scenario Best Practices

- Write step prose as a bare predicate: start with the verb ("opens", "sees", "approves"), never with a name.
- Read each line back as "Given \<virtual user\> \<prose\>" before committing it — if that sentence has the name twice, it's PKU681.
- Keep the virtual user in exactly one place per step: the `{ virtualUser: … }` option. That's what makes a step reusable across virtual users.
- Put reusable wording on the step's `template` so every call site inherits prose that never names the virtual user.
- Quotes and capitalisation are decoration, not an escape hatch — `` `'shopper' …` ``, `"Shopper …"` and `shopper's …` are all caught.

## Common Mistakes

A step named `'Susan searches for coffee'` run as `virtualUsers.susan` declares the subject twice. Use `'searches for coffee'`.

A possessive opening such as `` `shopper's cart is empty` `` still names the subject. Write `'has an empty cart'` with `{ virtualUser: virtualUsers.shopper }`.
