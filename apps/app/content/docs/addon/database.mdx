title: Database Tables
description: Shipping a table from an addon and folding it into the consumer's migrations
---

An addon can ship its own tables. It does not create them.

An addon has no database of its own — it runs inside the consuming application, against that application's database. If it created tables at boot it would put a second authority on a schema the consumer's migrations already own, and the consumer would have no record of what appeared or when. So an addon *declares* what it needs, `pikku db export` publishes that declaration, and the consumer's `pikku db generate` folds it into its own migration history, where it can be reviewed like any other migration.

## In the addon

### 1. Write the DDL

Put the addon's schema in `db/sqlite/` and `db/postgres/`, numbered the same way an application's migrations are:

```sql
-- db/sqlite/0001-labels.sql
CREATE TABLE labels (
  id TEXT PRIMARY KEY NOT NULL,
  name TEXT NOT NULL,
  color TEXT
);

CREATE UNIQUE INDEX labels_name_unique ON labels (name);
```

Write one directory per dialect you support. They are separate files because they are genuinely different SQL — the example above is `TEXT PRIMARY KEY NOT NULL` on sqlite and `TEXT PRIMARY KEY` on postgres.

An addon that supports only one dialect is fine, and it fails loudly rather than quietly: a consumer on a dialect the addon did not publish gets an error naming what the addon does support, because its tables cannot be created there and its functions would fail at runtime.

### 2. Publish it from the build

`pikku all` already does this. On every build it reads both migration directories and writes `<outDir>/db/pikku-db-meta.gen.json` — for each dialect, the SQL verbatim plus a table-and-column map used to work out what a consumer is already carrying.

If neither directory exists the artifact is written **empty**, and that is deliberate: an addon with no tables has to say so in a file that ships, because a consumer reads an absent file as a package that cannot answer the question at all.

`pikku db export` writes the same artifact on demand, if you want it outside a full build:

```bash
pikku db export
```

### 3. Ship the artifact

The consumer resolves the artifact **through the package name**, so it has to be both exported and packed:

```json
{
  "exports": {
    "./.pikku/db/pikku-db-meta.gen.json": "./dist/.pikku/addon/db/pikku-db-meta.gen.json"
  },
  "files": ["dist"]
}
```

:::warning[An unshipped artifact stops `db generate`]
Because the artifact is written unconditionally, a consumer that cannot resolve it knows the package cannot answer — the addon was built with an older CLI, or its `exports`/`files` do not carry the file. `db generate` fails and names both causes rather than continuing.

An addon that genuinely has no tables is not this case: it publishes `{}` and is waved through in silence.
:::

## In the consuming application

Wire the addon as normal — there is no separate registration for its schema:

```typescript @snippet rt-wire-addon-labels
```

Then:

```bash
pikku all           # records the addon declaration
pikku db generate   # writes a migration for every source not yet covered
pikku db migrate    # applies them
```

`db generate` writes one migration per addon, named after the package, carrying the addon's own SQL:

```sql
-- db/sqlite/0003-my-org-addon-labels.sql
-- Generated by `pikku db generate` from the '@my-org/addon-labels' addon.
-- Re-run the command after changing that source.

CREATE TABLE labels (
  id TEXT PRIMARY KEY NOT NULL,
  ...
```

It is a normal migration from that point on: yours to read, edit and commit.

### Ordering

Sources are generated in dependency order — Better Auth first, then the `@pikku/kysely` runtime tables, then addons. An addon table can therefore reference the auth `user` table or a runtime table. Order *between* addons is the order they were declared in, so an addon should not depend on another addon's tables.

### Changing an addon's schema

Re-running `db generate` after upgrading an addon writes only the delta. A wholly new table comes over as the addon's own `CREATE TABLE`, so its indexes and constraints survive; new columns on an existing table come over as `ALTER TABLE … ADD COLUMN`. A column that is `NOT NULL` with no default is emitted with a `REVIEW` comment above it, because it cannot be applied to a table that already has rows until you decide what those rows get.

When nothing has changed, `db generate` writes nothing and reports the addon as already covered.

### Remote addons contribute nothing

An addon wired with `wireRemoteAddon` executes in its own deployment, against its own database. Its artifact is ignored, and no migration is written for it, even when it publishes a complete one — the tables belong to the deployment that runs the functions, not to the caller.
