# Scenarios

A scenario is a workflow that drives your app the way users do. Its steps run as **virtual users** — synthetic users with real accounts — over the **real transport**: sign-in, auth middleware, permissions, serialization, everything. That makes one scenario definition useful three ways: an end-to-end test locally, a smoke test against staging, and a health check against production.

## Your First Scenario

Define a scenario with `pikkuScenario` — it has the same shape as a workflow function, but every `scenario.do` step names an exposed RPC **and who performs it**. `pikkuScenario` is generated into `#pikku/scenarios`, alongside `pikkuScenarioStep` and `pikkuFeature`. From the [online shop example](https://github.com/pikkujs/pikku/tree/main/examples/online-shop):

```typescript @snippet scenarioBasics
```

Because scenarios are workflows, steps are recorded durably — a replayed run returns cached step results instead of re-invoking them. `scenario.expectEventually` is the scenario-only polling step: it re-invokes the RPC as the virtual user until the predicate passes or the timeout fails the scenario (using it in a plain workflow raises [PKU675](/docs/pikku-cli/errors/pku675)). Tune the polling with `within` (total time budget, default `'30s'`) and `interval` (poll interval, default `'1s'`; a number is milliseconds) — both optional.

:::info[Virtual user steps never dispatch internally]
Every `scenario.do` in a scenario must carry `{ virtualUser }`. Steps without one are refused when running against an environment — a scenario run against staging or production can never accidentally touch local services or queues.
:::

:::warning[What a scenario body may do]
A scenario body runs against a live target, so it may only destructure `logger` and `config` from its services — anything else is a [PKU673](/docs/pikku-cli/errors/pku673) codegen error. Reach the app through virtual users instead. Every scenario must also assert: a flow of only `given`/`when` steps that never reaches a `then` (or an `expectEventually`/`expectError`/`expectService`/`expectScore` helper) is a [PKU680](/docs/pikku-cli/errors/pku680) error.
:::

:::warning[No state reset]
Scenarios run against live environments — including production. Nothing resets state afterwards, so scope what you create (unique titles, dedicated virtual user accounts) and clean up inside the scenario if it matters.
:::

## Conversing with AI Agents

For agent-powered apps, deterministic RPC calls only test half the product. `virtualUser.converse()` lets a virtual user hold a free-form conversation with one of your [AI agents](/docs/wiring/ai-agents) — in character. An LLM plays the virtual user (using the `personality` and `jobTitle` from its declaration), drives the agent over the real transport as the signed-in virtual user, answers the agent's tool-approval requests in character, and returns a verdict:

```typescript @snippet scenarioConverse
```

The verdict contains `passed`, the virtual user's `reasoning`, and the full `transcript` for debugging. The verdict is the virtual user's judgement — always follow up with a deterministic check through the same virtual user, as above.

`converse` also accepts:

| Option | Default | Description |
|--------|---------|-------------|
| `approvals` | `'in-virtual-user'` | How the virtual user answers tool-approval requests: `'in-virtual-user'` (decide as that person would), `'always'` (stress the happy path), `'never'` (exercise refusal handling) |
| `maxTurns` | `12` | Hard cap on conversation turns before forcing evaluation |
| `model` | virtual users service default | Model the virtual user uses for its own turns |

In a typed project, `agent` is constrained to the generated union of your agent names.

## Declared Steps and Features

When one intent spans several RPCs, or you want the same behaviour driven through a browser or the websocket, declare it as a `pikkuScenarioStep` instead of an inline `scenario.do`. A step declares one binding per surface (`default`, `browser`, `cli`), names itself with a `template` for the report, and is referenced from a scenario by name through `scenario.given`/`when`/`then`:

```typescript @snippet co-scenario-step
```

`pikkuFeature({ name, scenarios: [...] })` groups scenarios the way Gherkin's `Feature:` groups `Scenario:`. Browser bindings need `@pikku/playwright` installed; running with `--run default` (the default) skips scenarios containing browser steps rather than failing them.

## Steps for Addons and the Platform

Not everything that happens in a story is done by a person. Sometimes a third-party service acts ("Stripe confirms the payment"), and sometimes your own app acts on itself ("the shop ships the order"). Neither is one of your declared people, so neither runs as a virtual user. Each has its own declaration.

**`pikkuAddonScenarioStep`** is a step in which a third-party system acts. `addon` names the addon that wraps that service — the same name its `wireAddon` declares. These steps are the mock that consumers would otherwise hand-write, shipped and maintained with the addon:

```typescript @snippet addonScenarioStep
```

This arranges, it doesn't assert. "Stripe's webhook arrives" is a stub; "Then Stripe was charged" is an assertion, and only the first belongs in one of these steps.

**`pikkuPlatformScenarioStep`** is a step in which the app acts on itself — "Given the platform has expired the trial". The subject of that sentence is your app, not a user of it, so it gets its own declaration instead of a virtual user with an asterisk:

```typescript @snippet platformScenarioStep
```

:::info[Local tests only]
Both are local-test-only and never part of a virtual user's catalogue. A virtual user that could forge its own payment success, or expire its own trial, would be manufacturing the outcome it exists to discover.
:::

## Hooks

A hook is setup or teardown that runs around a scenario but isn't part of the story. Declare one with `pikkuScenarioHook` and attach it to a scenario as `before` or `after`. A hook runs outside the recorded steps, so tidying up never shows in the report as something the virtual user did.

`pikkuScenarioHook` returns the function you pass it unchanged — a hook is never registered. It exists so an inline hook is contextually typed, including the `virtualUsers` on its wire:

```typescript @snippet scenarioHook
```

Attach it by name: `pikkuScenario({ before: emptiesTheBasket, ... })`.

## Helpers for Steps

Most steps just call `virtualUser.invoke`. When a step has to reach past a virtual user — a route with no RPC, an identity no virtual user can hold, a thing that settles eventually — these helpers keep you from rewriting the same plumbing.

**`requireScenarioEnv(scenarioStep)`** returns the environment the run targets (so you get `apiUrl` and friends), or throws with a clear message if the run carries none. Pass it the `scenarioStep` from the step's wire.

**`postScenarioJson(url, { body, headers, method, fetch })`** POSTs JSON and reports what came back *without throwing on a 4xx/5xx*. A refusal is the expected outcome of a permissions scenario, so it has to survive as data — you get the status and body back instead of an exception.

```typescript @snippet scenarioPostJson
```

**`readScenarioHttpResponse(res)`** drains a `Response` into something a step can carry: the parsed body (an empty one counts as no body) alongside the text it was parsed from. Reach for it when you've called `fetch` yourself.

**`pollUntil(attempt, { timeoutMs, intervalMs })`** retries until `attempt` returns something other than `undefined`, or the timeout runs out (then it resolves `undefined`). It's for the eventually-consistent parts of a story — a queued job, a projection:

```typescript @snippet scenarioPollUntil
```

For polling an RPC as a virtual user, `scenario.expectEventually` is usually simpler. `pollUntil` is for when you're talking to something that isn't an RPC.

**`createCookieJar(apiUrl)`** gives a step a cookie store, so a bare `fetch` can hold a session across calls. Signing up is the classic case: a virtual user is already signed in before its first step, so sign-up is the one flow it can't perform. The jar keeps the `Set-Cookie` the sign-up returned and replays it on the next call, the way a browser would:

```typescript @snippet scenarioCookieJar
```

## Running Programmatically

`pikku scenario run` is the normal way in. If you're wiring a run up yourself, `createScenarioRunner(options?)` returns the two things the CLI needs — `{ workflowService, scenarioService }` — in one call. The workflow service is in-memory: a scenario run is a single external process driving a deployed app over its real transport, so there's nothing to persist and no second worker to resume it.

## Virtual Users and Environments

A virtual user is a declared person — a normal user row in your system, flagged `virtualUser: true` and signed in by the run. Declare the people once in code with `defineVirtualUsers`:

```typescript @snippet defineVirtualUsers
```

Target environments are top-level in `pikku.config.json`, and each virtual user's address is derived from its id and `scenarios.emailDomain`:

```json title="pikku.config.json"
{
  "environments": {
    "staging": { "apiUrl": "https://staging.example.com/api" },
    "production": {
      "apiUrl": "https://app.example.com/api",
      "appUrl": "https://app.example.com",
      "signInPath": "/api/auth/sign-in/virtual-user",
      "rpcPath": "/rpc",
      "production": true
    }
  },
  "scenarios": {
    "emailDomain": "virtual-users.example.com"
  }
}
```

The CLI generates a typed registry from `defineVirtualUsers`, and scenarios receive it as `virtualUsers` on the scenario wire. `signInPath` defaults to `/auth/sign-in/virtual-user` and `rpcPath` to `/rpc`; no signing key appears here. Sign-in is **lazy**: the first `invoke` signs the virtual user in (via the `pikkuVirtualUser` [Better Auth plugin](/docs/middleware/better-auth#virtual-users-synthetic-test-users)) and the session is cached for the rest of the run. `personality` and `jobTitle` shape the virtual user in `converse`.

## Running Scenarios

```bash
# List all pikkuScenario exports with names and descriptions
npx pikku scenario list

# Run all scenarios against an environment from pikku.config.json
VIRTUAL_USER_SIGNING_KEY=… npx pikku scenario run staging

# Filter by name or tag
npx pikku scenario run staging --flows shopperBuysAnItem
npx pikku scenario run production --tags checkout
```

| Option | Short | Description |
|--------|-------|-------------|
| `--flows` | `-f` | Comma-separated scenario names to run (default: all) |
| `--tags` | `-t` | Comma-separated tags — run scenarios matching any |
| `--features` | | Comma-separated feature names (`pikkuFeature` exports) — the feature is the run unit, so its hooks run once around the group |
| `--exclude-tags` | | Comma-separated tags to hold back — scenarios matching any are skipped, unless named directly with `--flows` |
| `--coverage` | | Reset/snapshot server coverage per scenario (the target must run with `--coverage`); writes `coverage/scenario-coverage.json` |
| `--run` | | Which surface every virtual user drives the system through: `browser`, `cli`, or `default` (server-side, the fast path). Defaults to `default` |
| `--strict` | | Fail rather than pass a `then` that has no witness for `--run` |
| `--spawn` | | Start `pikku dev` on the environment's `apiUrl` for the run and stop it afterwards |
| `--keep-alive` | | With `--spawn`, leave the server running after the run (dev loop) |
| `--trace` | | Keep every stack frame on a failure. Without it, only the project's own frames are shown |
| `--screenshots` | | Write the screenshots scenarios ask for to disk, under `.pikku/scenario-runs/<run>/<scenario>` |
| `--video` | | Which scenarios keep their recording: `failed` (the default), `all`, or `off` |
| `--api-url` | | Override the environment's `apiUrl` for this run |
| `--app-url` | | Override the environment's `appUrl` for this run — one url, or `<app>=<url>` pairs, comma-separated |

Scenarios run sequentially (they're stories; parallel virtual users would share cookie jars) and report `PASS`/`FAIL` per scenario with durations. A non-zero exit code on any failure makes them CI-friendly.

:::warning[Signing keys]
Virtual users sign in with a short-lived, single-use statement signed with an Ed25519 private key. For a local server, `pikku dev` creates the key pair and `scenario run` picks up the private half. For a deployed stage, set `VIRTUAL_USER_SIGNING_KEY` in the environment running the command — never put it in `pikku.config.json`. With neither, `scenario run` refuses to start. The stage holds only the public half, `VIRTUAL_USER_VERIFY_KEY`.
:::
