# AI Agents

Pikku AI Agents let you define conversational AI assistants that use your Pikku functions as tools, maintain conversation memory, support multi-agent orchestration, and stream responses in real time — all with the same transport-agnostic architecture as the rest of Pikku.

## What are AI Agents?

An AI agent is a conversational interface backed by a large language model (LLM). When a user sends a message, the agent reasons about it, optionally calls Pikku functions as tools, and streams a response back through a [channel](/docs/wiring/channels/).

**Key features:**

- **Functions as Tools**: Any wired Pikku function can be used as an agent tool — complete with schema validation and middleware
- **Multi-Agent Orchestration**: Agents can delegate to sub-agents, each with their own tools and memory
- **Conversation Memory**: Persistent thread-based message history with configurable storage backends
- **Working Memory**: Structured state that the agent maintains across turns (e.g., user preferences, task progress)
- **Real-Time Streaming**: Token-by-token streaming via Pikku channels with full middleware support
- **Human-in-the-Loop**: Tool approval flows that suspend execution until a user approves or denies a tool call
- **Model Configuration**: Centralized model aliases, per-agent overrides, and multi-provider support
- **AI Middleware**: Hooks to modify inputs, filter the output stream, and post-process results

## Core Concepts

### Agent Definition

Every agent is defined with `pikkuAgent()` and requires at minimum:

| Property | Type | Description |
|----------|------|-------------|
| `name` | `string` | Unique identifier for the agent |
| `description` | `string` | Human-readable description (also shown to parent agents) |
| `goal` | `string` | System prompt that guides the agent's behavior |
| `model` | `string` | Model identifier in `provider/model` format (e.g., `openai/gpt-4o-mini`) |

Optional properties:

| Property | Type | Default | Description |
|----------|------|---------|-------------|
| `tools` | `Function[]` | — | Pikku functions the agent can call |
| `agents` | `Agent[]` | — | Sub-agents this agent can delegate to |
| `memory` | `AgentMemoryConfig` | — | Conversation and working memory config |
| `maxSteps` | `number` | `10` | Maximum tool-call iterations per message |
| `toolChoice` | `'auto' \| 'required' \| 'none'` | `'auto'` | How the model selects tools |
| `temperature` | `number` | — | Model temperature override |
| `output` | `Schema` | — | Structured output schema for the agent's response |
| `tags` | `string[]` | — | Tags for filtering and organization |
| `middleware` | `Middleware[]` | — | Pikku middleware applied to the agent |
| `channelMiddleware` | `ChannelMiddleware[]` | — | Middleware for the streaming channel |
| `agentMiddleware` | `PikkuAgentMiddlewareHooks[]` | — | Hooks around each step and each tool call |
| `permissions` | `PermissionGroup` | — | Permission requirements for accessing the agent |

### Tools

Agents use your existing Pikku functions as tools. When you pass a function reference to the `tools` array, Pikku automatically:

1. Extracts the function's input schema from its wired metadata
2. Uses the function's description as the tool description for the LLM
3. Executes the function through the standard Pikku function runner (with middleware, validation, etc.)

Pass the functions in the `tools` array, as in the example above: `tools: [listItems, getItem]`. Any wired Pikku function can be a tool.

### Multi-Agent Orchestration

Agents can delegate to sub-agents using the `agents` property. The parent agent sees each sub-agent as a tool it can call with a message and a session label:

```typescript @snippet wb-agent-multi
```

When the parent calls a sub-agent, it provides:
- **message**: The task or question to send
- **session**: A short label for thread continuity (reusing the same session continues the conversation)

Sub-agent calls are streamed through scoped channels, so the client receives events tagged with the sub-agent's name and session.

### Conversation Memory

Agents persist conversations in threads using an `AgentStorageService`. Configure memory via the `memory` property:

Set `memory: { storage: 'agentStorage', lastMessages: 10 }` on the agent, as in the example at the top of this page. `storage` is the name of the storage service in your singleton services, and `lastMessages` is how many recent messages go into the context.

| Property | Type | Description |
|----------|------|-------------|
| `storage` | `string` | Key of the `AgentStorageService` in your singleton services (defaults to `'agentStorage'`) |
| `lastMessages` | `number` | How many recent messages to load from the thread (default: `20`) |
| `workingMemory` | `Schema` | Enable structured working memory with a JSON schema |

#### Working Memory

Working memory lets agents maintain structured state across conversation turns — like user preferences, task lists, or accumulated context. When enabled, the agent receives its current working memory in the system prompt and can update it by outputting `<working_memory>` tags:

Add a `workingMemory` schema (a Zod or JSON schema) to the agent's `memory` config, next to `storage` and `lastMessages`.

The agent outputs partial JSON updates. Setting a field to `null` deletes it. Updates are deep-merged with the existing state and validated against the schema.

### Streaming

Agents stream responses through Pikku channels. The stream emits `AgentStreamEvent` objects:

| Event Type | Description |
|------------|-------------|
| `text-delta` | Incremental text token from the model |
| `reasoning-delta` | Reasoning/thinking token (for models that support it) |
| `tool-call` | Agent is calling a tool (includes name and args) |
| `tool-result` | Tool execution result |
| `agent-call` | Parent agent is calling a sub-agent |
| `agent-result` | Sub-agent has completed |
| `approval-request` | A tool requires user approval before execution |
| `usage` | Token usage statistics for the current step |
| `error` | An error occurred during execution |
| `suspended` | Execution suspended (e.g., missing RPC functions) |
| `done` | Stream is complete |

Events from sub-agents include `agent` and `session` fields so clients can track which agent produced which output.

### Streaming over a channel

You don't have to write the streaming plumbing yourself. `agentStream` is a ready-made function that runs an agent and sends its events (`text-delta`, `tool-call`, `usage` and the rest from the table above) to the client as they happen, instead of making the caller wait for the whole run. It's the streaming counterpart of `agent`. Wire it to a channel (or any transport that can carry a stream) and you're done:

```typescript @snippet aiAgentStream
```

The agent name is typed against your generated agent map, so a typo is a compile error. The function takes `{ agentName?, message, threadId, resourceId }`; leave the name out of the call (`agentStream()`) and the client picks the agent by passing `agentName` in its input.

### Tool Approval (Human-in-the-Loop)

You can require user approval before certain tools execute. This is configured via the `requiresToolApproval` option when streaming:

Call `rpc.agent.stream(agentName, { message, threadId, resourceId }, { requiresToolApproval: 'explicit' })`. The third argument carries the approval mode.

| Mode | Behavior |
|------|----------|
| `'explicit'` | Only tools marked with `approvalRequired: true` in their function config need approval (default) |
| `'all'` | Every tool call requires approval |
| `false` | No approval required |

When a tool requires approval:

1. The agent stream emits an `approval-request` event with the tool name, args, and a reason
2. Execution suspends — the run state is saved with `status: 'suspended'`
3. The client presents the approval request to the user
4. The user approves or denies via `rpc.agent.resume()`
5. If approved, the tool executes and the agent continues; if denied, the agent receives a denial message and continues

Answer the approval with `rpc.agent.resume(runId, { toolCallId, approved: true })`, passing the run id from the `approval-request` event and the id of the tool call being answered. Pass `approved: false` to deny it.

### Readable approval prompts

By default the approver sees a tool name and raw arguments, which isn't much to decide on. Give the function an `approvalDescription` and the `approval-request` event carries a sentence a person can read instead. Build it with `pikkuApprovalDescription`; it receives your services and the exact input of the pending call:

```typescript @snippet approvalDescription
```

Like the other `pikku*` factories, it exists so the build can tree-shake the services it uses. If the description throws, the approval is still raised, just without the text. A gate never disappears because its label failed to render.

### Answering a paused run

A run that hits a gated tool stops and waits, and something has to answer. Pikku ships two ready-made functions for that, so you only wire them to whatever transport your approvers use:

- `agentResume()` answers **one** pending approval: `{ runId, toolCallId, approved }`. The run then carries on.
- `agentApprove(agentName)` answers **every** pending approval for a run in one call: `{ runId, approvals: [{ toolCallId, approved }] }`. Handy when the model asked for several things in the same step.

```typescript @snippet aiAgentApprove
```

Both need a session and RPC, so they sit behind your normal auth like any other function.

## Required Services

AI Agents require three services in your singleton services:

| Service | Interface | Purpose |
|---------|-----------|---------|
| `agentRunner` | `AgentRunnerService` | Executes the LLM (e.g., `VercelAgentRunner` from `@pikku/ai-vercel`) |
| `agentStorage` | `AgentStorageService` | Persists threads, messages, and working memory (e.g., `PgKyselyAgentStorageService` from `@pikku/kysely-postgres`) |
| `agentRunState` | `AgentRunStateService` | Tracks agent run status and pending approvals (e.g., `PgKyselyAgentStorageService` also implements this) |

### Setup Example

The setup has four parts:

1. Create a Kysely instance (`PikkuKysely` from `@pikku/kysely-postgres`) and `init()` it.
2. Create a `PgKyselyAgentStorageService` from its `kysely` and `init()` it.
3. Create a `VercelAgentRunner` from `@pikku/ai-vercel`, giving it your providers as a map of AI SDK clients, for example `{ openai: createOpenAI({ apiKey }), anthropic: createAnthropic({ apiKey }) }`.
4. Pass them to `createSingletonServices` as `agentStorage`, `agentRunState` (the same storage service implements both) and `agentRunner`.

The `VercelAgentRunner` from `@pikku/ai-vercel` uses the [Vercel AI SDK](https://sdk.vercel.ai/) under the hood, supporting any provider compatible with the AI SDK (OpenAI, Anthropic, Ollama, Google, etc.).

Model identifiers use `provider/model` format (e.g., `openai/gpt-4o-mini`, `anthropic/claude-sonnet-4-20250514`, `ollama/llama3`).

## Credential Integration

When an agent calls a tool that belongs to an addon requiring a [credential](/docs/wiring/credentials/), Pikku automatically checks whether the current user has that credential connected. If not, the agent run suspends with a `ToolCredentialRequired` error and the stream emits a `credential-request` event:

```json
{
  "type": "credential-request",
  "credentialName": "google-sheets",
  "credentialType": "oauth2",
  "connectUrl": "/auth/oauth2/google-sheets/authorize"
}
```

The client can then redirect the user to connect the credential. Once connected, resume the agent:

Once the user has connected the credential, resume the run with `rpc.agent.resume(runId, { toolCallId, approved: true })`.

This is fully automatic — you don't write credential-checking logic in your tools or agent definitions.

## Voice Support

Two agent middlewares ship in core, turning any agent into a voice assistant.
They come from `@pikku/core/agent` and go on the agent's `agentMiddleware` list:

```typescript @snippet wb-agent-voice
```

**`voiceInput(config?)`** — transcribes any audio attachment on the incoming
message. Accepts `language`, `model` and `allowedAudioHosts`.

**`voiceOutput(config?)`** — intercepts the output stream and synthesizes text
into audio events as sentences finish. Accepts `model`, `voice`, `format`,
`instructions`, `speed`, `language`, `speakableScripts` and `always`.

Neither needs a service of its own: both read `agentRunner` and use its optional
modality methods — `transcribe` for input, `generateSpeech` for output. A runner
without them is a no-op rather than an error, so check your
[`AgentRunnerService`](/docs/api/ai-services) implements the one you need.
`@pikku/ai-deepinfra` supplies DeepInfra speech and transcription models for use
with the Vercel AI SDK runner.

Two behaviours worth knowing before you wire this up:

- **`voiceOutput` speaks only what was spoken to.** One agent usually serves both
  kinds of caller — the same thread typed at from a desk and talked to from a
  phone — and synthesizing a reply nobody is listening to costs money on every
  sentence of every turn. Sending audio is how a client says it is in a call; no
  extra flag is needed. Set `always: true` for cases where speech is not a reply
  to speech at all: a read-aloud accessibility mode, a kiosk.
- **`speakableScripts` guards pronunciation.** Name the scripts your model can
  actually pronounce and the voice each needs, and anything written in another
  script is left unspoken and reported once as a `voice-unsupported` data event,
  rather than sent to a model that will mangle it. Omit it and every model is
  trusted with every script — the right default for a genuinely multilingual
  provider.

### Custom UI with Hooks

For full control, use the runtime hook directly:

Call `usePikkuAgentRuntime({ api, agentName, threadId, resourceId })` to get a runtime, then render `<Thread />` from `@assistant-ui/react` inside an `<AssistantRuntimeProvider runtime={runtime}>`.

### Tool Approval UI

The approval context tracks pending tool approvals and credential requests:

`usePikkuApproval()` returns `pendingApprovals` and `handleApproval`. Render one entry per pending approval, keyed by `toolCallId`. For an entry whose `type` is `'credential-request'`, show a link to its `connectUrl`. For any other, show Approve and Deny buttons that call `handleApproval(approval.toolCallId, true)` or `handleApproval(approval.toolCallId, false)`.

## Scoring Agent Runs

A scorer grades a finished agent run and returns a `{ score, reason }` pair. There are two ways to declare one, and both give you the same kind of thing back, so the rest of Pikku treats them alike.

| | `pikkuAgentScorer` | `pikkuAgentJudge` |
|---|---|---|
| Who grades | A function you write, in-process | Another model |
| Good for | Anything you can check in code: did the run call the right tool, stay under a step budget, mention a product | Qualities code can't express: is the answer helpful, on-brand, actually responsive |
| Core field | `score(input, services)`, which reads the run and returns `{ score, reason }` | `goal`, the rubric: what a good answer looks like, phrased as the goal it should meet |
| Services | Gets your own services as the second argument | Runs on the model you name in `model` |

Both take:

- `name`: unique per project, and how the score is identified in results.
- `description`: one line for whoever reads the score later.
- `sampleRate`: a number from 0 to 1, the fraction of live runs to grade. It defaults to all of them, so turn it down for expensive judges.
- `requiresReference`: grade against a known-correct answer. A scorer that needs one is test-only. Live traffic has no answer key, so the runtime never samples it.

A judge adds a few more:

- `model`: the model that grades. It is not the model under test.
- `prompt`: replaces the generated rubric prompt outright when `goal` can't express the framing you want. The `{ score, reason }` response is still forced.
- `toolCalls`: how much of the run's trajectory the judge sees. `off` shows none, `names` shows which tools were called, `full` shows everything. It defaults to `names`: enough to tell a tool-backed answer from an invented one, without sending a third-party model the rows your tools returned.

Pick a scorer first. It's free, deterministic and fast. Reach for a judge when the thing you care about is a judgement call, and use `sampleRate` to keep the cost in check.

## Agents as Workflow Nodes

A [graph workflow](/docs/wiring/workflows/graph-workflows) node can reference an agent by name, just like an RPC function or a sub-workflow. The node runs the agent with the standard agent input (`message`, `threadId`, `resourceId`), and the node's result is the agent's output — so downstream nodes can `ref()` its fields:

Declare the workflow with `pikkuWorkflowGraph`. In `nodes`, map a node name to the agent's name (for example `classify: 'ticket-classifier'`) or to an RPC function (`escalate: 'ticketEscalate'`). In `config`, give each node an `input` function that builds its input from `ref(...)`: for the agent node, `message`, `threadId` and `resourceId` from the workflow input, and `next: 'escalate'` to continue. The `escalate` node then reads the agent's `category` with `ref('classify', 'category')`.

Declare an `output` schema on the agent when downstream nodes need typed access to its result — `ref()` resolves the agent's output keys. See [Graph Workflows](/docs/wiring/workflows/graph-workflows) for the full graph syntax.
