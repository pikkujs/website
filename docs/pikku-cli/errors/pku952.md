# PKU952: Secret Key Not Static

## Error Message

```
[PKU952] src/services.ts reads a secret with a non-literal key (`${provider}_API_KEY`). The deployment cannot narrow its secret scope around a key it cannot see.
```

This is a **warning**. It prints on every build, but only fails the build with `--fail-on-warn`.

## What Went Wrong

`secrets.getSecret(...)` was called with a computed key — a template literal, a variable, a property lookup — rather than a string literal.

Pikku reads secret usage statically so the deployment can grant each service access to exactly the secrets it names, and no more. A computed key defeats that: the tooling can't tell whether the code reads one secret or every secret in the vault, so it can't narrow the scope. In practice that means the deployed role ends up with broad vault access, and the "which secrets does this service need?" question has no answer anyone can check.

It also means the key can't be declared with `defineSecret`, so you'll usually see [PKU951](./pku951.md) alongside this.

## How to Fix

Make the key literal at each call site. A `switch` or a lookup of literals is fine — what matters is that each `getSecret` argument is a literal:

```typescript title="src/services.ts"
// ✅ Correct — every key is visible to the scanner
const stripeKey = (await secrets.getSecret('STRIPE_API_KEY')).reveal()
const sendgridKey = (await secrets.getSecret('SENDGRID_KEY')).reveal()
```

### If the provider genuinely varies

Branch on the provider and read a literal in each arm:

```typescript title="src/services.ts"
const providerKey = async (provider: 'stripe' | 'adyen') => {
  switch (provider) {
    case 'stripe':
      return (await secrets.getSecret('STRIPE_API_KEY')).reveal()
    case 'adyen':
      return (await secrets.getSecret('ADYEN_API_KEY')).reveal()
  }
}
```

This is longer than the template literal it replaces, and that's the point: both keys are now declarable, provisionable and scopeable, and a new provider can't quietly widen the service's vault access.

## Secret Handling Best Practices

- Treat the secret key as configuration structure, not data — enumerate it rather than computing it.
- Declare every literal key with `defineSecret` so it's validated and surfaced (see [PKU951](./pku951.md)).
- Resolve secrets at construction time in `services.ts` or middleware, then pass configured clients onward.
- Run CI with `--fail-on-warn` if your project treats secret scoping as non-negotiable.

## Common Mistakes

```typescript title="wrong.ts"
// ❌ Wrong — the scanner sees one unknowable key, so the scope can't be narrowed
const key = (await secrets.getSecret(`${provider.toUpperCase()}_API_KEY`)).reveal()
```

```typescript title="correct.ts"
// ✅ Correct — one literal per branch
const key =
  provider === 'stripe'
    ? (await secrets.getSecret('STRIPE_API_KEY')).reveal()
    : (await secrets.getSecret('ADYEN_API_KEY')).reveal()
```
