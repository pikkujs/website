# PKU954: PII Into Sink

## Error Message

```
[PKU954] Function 'sendReceipt' passes personal data to 'logger.info' at line 31 (path 'shopper.email').
  A log, the console and a webhook all leave your control — they are shipped to third parties and retained long past the request. Log an id instead, or narrow the value to a non-identifying field. An email to the data subject, an audit in your own database and a queue on your own infrastructure are fine.
```

This is an **error**-severity diagnostic. It fails the build with `--fail-on-error`, and it only runs when the classification scan is requested — `pikku all --security`.

## What Went Wrong

A function passed a value branded `Pii<T>` — a column your schema classifies as personal data — to a sink that leaves your control:

- **a logger**, which is read far more widely than the row it came from, is usually shipped to a third-party aggregator, and is retained long past the lifetime of any consent;
- **`console`**, which is the same thing with no service in front of it;
- **a webhook**, which posts the value to somebody else's server.

Unlike [PKU953](./pku953.md), nothing here needed a `.reveal()`. `Pii<T>` is simply the brand the generated row types carry, so a column read straight out of the database keeps it through a local binding and into the call — which is exactly why this is easy to do by accident.

## What Is *Not* Reported

PII is not a secret, so the rule is not "never write it down". The question is whether writing it *there* hands it to somebody else, and three sinks are deliberately quiet:

- **an email** is addressed to the data subject — their own name in it is the point;
- **an audit** is a row in your own database, and naming who did what is usually the legal requirement rather than a breach of it;
- **a queue payload** stays on your own infrastructure and is consumed by your own worker.

`private` columns are never reported at any sink. `private` says who may *read* the row; it is not a claim that recording the value is a disclosure.

## How to Fix

Log the identifier, not the person:

```typescript title="src/functions/receipts.functions.ts"
export const sendReceipt = pikkuFunc({
  func: async ({ logger, email, db }, data) => {
    const shopper = await db
      .selectFrom('shopper')
      .selectAll()
      .where('shopperId', '=', data.shopperId)
      .executeTakeFirstOrThrow()

    await email.send({ to: shopper.email, template: 'receipt' }) // ✅ addressed to them

    logger.info(`receipt sent to shopper ${shopper.shopperId}`) // ✅ an id, not a name
    return { ok: true }
  },
})
```

### If you're logging a whole row

A row type is branded wherever any of its columns are, so logging the object logs the PII inside it. Log the fields you actually need:

```typescript
// ❌ logger.info('loaded shopper', shopper)
logger.info(`loaded shopper ${shopper.shopperId}`)
```

### If a webhook consumer genuinely needs the value

That is a disclosure to a third party, and it wants a decision rather than a log line: send a reference the consumer resolves against your API under its own authorization, or record the lawful basis and route it through a service that is allowed to make the call.

### If the finding is wrong

An explicit annotation erases the brand, because the brand is optional by design:

```typescript
const email: string = shopper.email // the scan goes quiet from here
```

That is the documented limit of a structural marker: it catches the mistake, not someone determined to silence it. Reach for it only when the column is genuinely not personal data — in which case the better fix is to correct its classification in `db/annotations.ts` and re-run `pikku db migrate`.

## Common Mistakes

```typescript title="wrong.ts"
// ❌ Wrong — the address lands in the log aggregator, past any consent
logger.info('sending receipt', { email: shopper.email })
```

```typescript title="correct.ts"
// ✅ Correct — the id is enough to find the row again
logger.info('sending receipt', { shopperId: shopper.shopperId })
```
