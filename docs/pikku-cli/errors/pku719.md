# PKU719: Split Type Identity

## Error Message

```
[PKU719] A dependency resolves a shared package at a different version than this project:
  "@acme/auth-kit" is linked to /Users/me/code/auth-kit and resolves better-auth@1.6.27 there, while this project resolves better-auth@1.6.23 — two type identities for better-auth
TypeScript treats each pair as two unrelated types and structurally compares them
wherever they meet, which inside a generic inference chain can exhaust the heap —
codegen then dies of memory pressure instead of reporting an error.

Fix: align the versions so the install resolves one copy, or drop the link and
reinstall. Set PIKKU_SKIP_TYPE_IDENTITY_CHECK=1 to silence this.
```

With more than one mismatch the first line reads `Dependencies resolve shared packages at a different version than this project:` and each pair gets its own indented line.

## What Went Wrong

Two copies of the same package, at different versions, are reachable from your project — so TypeScript has **two declarations of the same interface** and no reason to believe they are related. Values that are structurally identical stop assigning to each other, and, much worse, every place the two meet becomes a full structural comparison of the whole shape. Inside a generic inference chain that compounds: a real project went from a 1.3GB/13s typecheck to an unbounded OOM (8GB and 12GB ceilings both died, 7.7M types, single assignability checks taking 8 seconds).

That is why Pikku warns *before* running codegen. A V8 heap OOM aborts the process — it doesn't fail it — so nothing printed afterwards would ever reach you. It reads as "codegen got slow", never as a version problem.

Pikku only checks packages whose *type* identity matters, not just their runtime identity: `better-auth`, `@better-auth/core`, `@pikku/core`, `kysely` and `zod`. Two situations can put a second copy of one of them in front of TypeScript:

- **A linked dependency.** A dependency whose code physically lives **outside** your project — a `link:` or `portal:` dependency, or a hand-made symlink into a sibling checkout — resolves its imports from *its own* checkout, which your lockfile has no say over. The symlink is often not the package directory but its build output (`node_modules/@scope/pkg/dist -> ../../../other-repo/packages/pkg/dist`), which still moves type resolution into the other tree because TypeScript resolves symlinks to their realpath. The message names the linked directory.
- **An installed Pikku package with its own copy.** An isolated install (bun's default, pnpm) gives each package its own store entry, and a Pikku package that declares `zod` can resolve a different `zod` there than your app does. `@pikku/cli` is the one that hurts: codegen then reads your app's schemas with a different zod than wrote them, and a perfectly correct schema fails with `Could not convert Zod schema`. The message reads `@pikku/cli resolves zod@4.4.3, while this project resolves zod@4.6.5 — two copies of zod in one install`.

`pikku validate` reports both as errors (`split-type-identity-…` and `skewed-type-identity-…`), so a CI run that validates catches them before anything is built.

This is deliberately a warning, not a hard failure: a skewed linked dependency is a strong signal, not a certainty, and plenty of them are harmless.

## How to Fix

The message names both sides. Pick one version and make both trees resolve it.

### If you linked a sibling checkout

This is the case the check actually detects. Bump the shared package in whichever tree is behind, then reinstall **in that tree** so its own `node_modules` updates:

```bash
# option A — bring the linked checkout up to what this project uses
cd /Users/me/code/auth-kit
npm install better-auth@1.6.23
npm ls better-auth

# option B — bring this project up to what the link uses
cd /Users/me/code/my-app
npm install better-auth@1.6.27
```

Reinstalling only in your app is the most common wasted attempt: the linked package keeps resolving from its own checkout, so nothing changes.

If the link was a temporary debugging convenience, drop it entirely and let the registry copy come back — that removes the second tree altogether:

```bash
npm uninstall @acme/auth-kit
npm install @acme/auth-kit
```

### If an installed Pikku package carries its own copy

Nothing is linked here, so there is no second tree to reinstall. Pin one version for the whole install and reinstall, so the store entry is rebuilt against it:

```json title="package.json (bun / npm)"
{
  "overrides": { "zod": "4.6.5" }
}
```

```bash
rm -rf node_modules && bun install
bunx pikku validate   # the skewed-type-identity error is gone
```

Use the version your app resolves — the one the message names after `this project resolves`. Yarn spells the field `resolutions`, pnpm `pnpm.overrides`, as below.

### If you have a duplicate inside one monorepo

Two workspaces asking for different ranges of the same package leave the package manager no choice but to install both. Find who is asking for what, then converge them:

```bash
npm ls @pikku/core          # every path that resolves a copy
yarn why @pikku/core
pnpm why -r @pikku/core
```

Then pin one version for the whole tree:

```json title="package.json (npm)"
{
  "overrides": { "better-auth": "1.6.27", "@pikku/core": "0.12.36" }
}
```

```json title="package.json (yarn)"
{
  "resolutions": { "better-auth": "1.6.27", "@pikku/core": "0.12.36" }
}
```

```json title="package.json (pnpm)"
{
  "pnpm": { "overrides": { "better-auth": "1.6.27", "@pikku/core": "0.12.36" } }
}
```

Reinstall from a clean slate so the deduped layout is actually built, then confirm exactly one copy:

```bash
rm -rf node_modules && npm install
npm dedupe
npm ls better-auth   # expect a single line, deduped at the root
```

### If a package you publish depends on a shared type

A library that puts a type-carrying package in `dependencies` gets its own private copy when a consumer resolves a different version. Declare it as a peer instead, so the consumer's single copy is the one everybody uses:

```json title="packages/auth-kit/package.json"
// ❌ Wrong — causes PKU719: every consumer can end up with a second copy
{
  "dependencies": { "better-auth": "1.6.27", "zod": "^3.23.0" }
}
```

```json title="packages/auth-kit/package.json"
// ✅ Correct — one copy, owned by the consumer
{
  "peerDependencies": { "better-auth": "^1.6.0", "zod": "^3.23.0" },
  "devDependencies": { "better-auth": "1.6.27", "zod": "3.23.8" }
}
```

### If you need to build right now

The check is a heuristic, so it can be silenced while you deal with the real fix:

```bash
PIKKU_SKIP_TYPE_IDENTITY_CHECK=1 npx pikku all
```

Do this knowingly — if your codegen is OOMing, silencing the warning removes the only explanation you were going to get.

## Dependency Best Practices

- Keep every shared, type-carrying package (`@pikku/core`, `zod`, `kysely`, `better-auth`) on **one** version across the whole workspace — a catalog, syncpack, or a single `overrides` block is enough.
- Prefer `peerDependencies` over `dependencies` for those packages in anything you publish or link; `dependencies` is what creates the second copy.
- After linking a sibling checkout, run `npm ls <pkg>` in **both** trees, not just yours.
- Reach for `npm dedupe` (or a clean `rm -rf node_modules && install`) after any version bump that touched a shared package — an incremental install often leaves the nested copy in place.
- Treat a sudden jump in typecheck time or memory as a dependency-graph question first. Structural comparison of duplicated types is the usual cause, and it never surfaces as a type error.

## Common Mistakes

Assuming that because both copies are "the same type", assignment will work:

```typescript title="src/services.ts"
// ❌ Wrong — causes PKU719: `auth` is built against the linked checkout's better-auth
import { createAuth } from '@acme/auth-kit' // resolves better-auth@1.6.27
import type { Session } from 'better-auth' // resolves better-auth@1.6.23

const session: Session = await createAuth().getSession(request)
// Type 'Session' is not assignable to type 'Session' — two identical shapes,
// two identities. And in a generic chain, this comparison is what blows the heap.
```

```typescript title="src/services.ts"
// ✅ Correct — both trees resolve better-auth@1.6.27, so there is one Session
import { createAuth } from '@acme/auth-kit'
import type { Session } from 'better-auth'

const session: Session = await createAuth().getSession(request)
```

The other classic: fixing the version in your app's `package.json`, seeing the warning persist, and concluding the check is wrong. The warning prints the linked directory for a reason — the second copy lives there, and only an install *in that directory* removes it.
