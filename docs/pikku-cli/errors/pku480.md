# PKU480: Column Name / Type Contradiction

## Error Message

```
[PKU480] Column "public.users.created_at" is named like a date but its DB type is boolean (boolean). If intentional, set its kind in db/annotations.ts.
```

## What Went Wrong

While generating your Kysely DB types, Pikku noticed a column whose **name** strongly implies one type but whose **actual database type** is something else. Here, `created_at` reads like a timestamp, yet Postgres reports it as a `boolean`. That mismatch is almost always a sign that a migration drifted, a column was repurposed, or the wrong type was chosen — the kind of thing that silently produces wrong types at every call site.

This is a **warning**, not a blocker (it only fails the build under `--fail-on-warn`). Pikku won't override your schema — the database is the source of truth — but it flags the contradiction so you can confirm it's intentional. The check only runs on Postgres, where the real column type is known. On SQLite the storage type is indeterminate (dates are just `TEXT`), so there's nothing concrete to contradict and this warning never fires.

## How to Fix

If the type is intentional, silence the warning by declaring the column's `kind` (or `tsType`) in `db/annotations.ts` — the hand-editable annotations file. If it's a mistake, fix the schema with a migration or rename the column.

```typescript title="db/annotations.ts"
// ❌ Wrong — no annotation, so Pikku warns on the name/type contradiction
export const annotations = {
  'public.users': {
    // created_at is really a boolean, but nothing acknowledges that
  },
}
```

```typescript title="db/annotations.ts"
// ✅ Correct — the boolean type is intentional and acknowledged
export const annotations = {
  'public.users': {
    created_at: { kind: 'boolean' },
  },
}
```

Then regenerate the types:

```bash
pikku db migrate
```

If the column was meant to be a timestamp, don't annotate around it — rename or retype it in a SQL migration so `created_at` is an actual `timestamp`, then re-run `pikku db migrate`.

## Database Schema Best Practices

- Keep column names honest: a `_at` suffix should be a date/time, an `is_`/`has_` prefix should be a boolean — the name is documentation.
- When a column's type genuinely differs from what its name implies, declare it explicitly in `db/annotations.ts` so intent is recorded in code review.
- Fix drift at the schema level with a migration whenever you can; annotations are for intentional exceptions, not for papering over mistakes.

## Common Mistakes

Editing the generated schema instead of the annotations file. `db/schema.d.ts` is regenerated on every `pikku db migrate`, so any hand-edit there is silently overwritten.

```typescript title="db/schema.d.ts"
// ❌ Wrong — hand-editing the generated file; wiped on the next migrate
export interface UsersTable {
  created_at: boolean // manually "fixed" here — will not survive
}
```

```typescript title="db/annotations.ts"
// ✅ Correct — declare intent in the hand-editable annotations file
export const annotations = {
  'public.users': {
    created_at: { kind: 'boolean' },
  },
}
```
