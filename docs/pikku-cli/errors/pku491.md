# PKU491: Schema Transform Not Supported

## Error Message

```
[PKU491] 'CreateAssessmentInput' contains a .transform() at .when.
A transform makes the value sent and the value received two different shapes, and a wire contract describes one: it cannot be expressed in JSON Schema or in the generated TypeScript.
Validate with the plain schema and apply the transform inside the function, or move it to the output type.
```

The path after `at` tells you exactly where the transform lives: `.when` for a field, `.user.email` for a nested field, `.items[]` for an array element, `[key]` for a record key, and **`the schema itself`** when the whole schema is a transform (`z.string().transform(...)` used directly as `input`).

## What Went Wrong

A Zod schema wired to a function's `input` or `output` contains a `.transform()` somewhere inside it.

A Zod schema with a transform has *two* types: an input type (what you hand to `parse`) and an output type (what comes back). `z.string().transform((s) => new Date(s))` accepts a `string` and produces a `Date`. That's perfectly good validation code — it's just not a contract. Pikku publishes your `input` schema as JSON Schema (for the OpenAPI document and client-side validation) and as a generated TypeScript type for the fetch/WebSocket clients. Both can only describe **one** shape, so there is no honest answer to "what does this endpoint accept?" when the schema quietly rewrites the value on the way in.

Pikku detects this up front rather than letting it through, because the downstream failures were worse than the cause: `z.toJSONSchema` with `unrepresentable: 'any'` turns a transform into `{}` — a schema that accepts literally anything — and the TypeScript conversion throws an error about TypeScript rather than about your wiring. You'd get a permissive endpoint, or a confusing unrelated error (previously a bad-`#pikku/*`-import complaint), instead of a message naming the schema and the field.

## How to Fix

Keep the schema describing the wire shape, and do the conversion in the function body — where you have services, can throw a real Pikku error, and where the conversion is visible to anyone reading the handler.

```typescript title="assessments.schemas.ts"
// ❌ Wrong — causes PKU491
import * as z from 'zod'

export const CreateAssessmentInput = z.object({
  patientId: z.string(),
  when: z.string().transform((s) => new Date(s)),
})
```

```typescript title="assessments.schemas.ts"
// ✅ Correct — the schema describes what's on the wire
import * as z from 'zod'

export const CreateAssessmentInput = z.object({
  patientId: z.string(),
  when: z.string().datetime(),
})
```

```typescript title="assessments.functions.ts"
// ✅ Correct — the conversion happens where the value is used
import { pikkuFunc } from '#pikku/pikku-types.gen.js'
import { CreateAssessmentInput } from './assessments.schemas.js'

export const createAssessment = pikkuFunc({
  func: async ({ database }, { patientId, when }) => {
    const scheduledAt = new Date(when)
    return database.insert('assessment', { patientId, scheduledAt })
  },
  input: CreateAssessmentInput,
})
```

### Constraints instead of coercion

Most transforms exist to accept a looser input than the real type. Say the constraint in the schema instead, and the generated client and OpenAPI doc get to say it too:

```typescript
// ❌ Wrong — each of these is a transform
z.string().transform((s) => s.trim())
z.string().transform((s) => Number(s))
z.string().transform((s) => s.split(','))

// ✅ Correct — describable constraints, converted in the function
z.string().trim().min(1)   // `.trim()` is a check, not a transform
z.number()                 // send a number; don't accept a string and cast it
z.array(z.string())        // send an array; don't accept a joined string
```

`z.date()` is fine as-is — Pikku maps it to `{ type: 'string', format: 'date-time' }` in JSON Schema — so you rarely need a string-to-Date transform at the boundary at all.

### What is and isn't a transform

Detection walks the whole schema tree, so a transform nested behind wrappers still trips it. These are **not** transforms and are safe to use:

- `.optional()`, `.nullable()`, `.nullish()`, `.readonly()`
- `.default(...)` and `.prefault(...)` — Pikku drops defaulted fields from `required`, so a client may omit them
- `.refine(...)` and `.superRefine(...)` — checks, not rewrites: same type in, same type out
- `.min()`, `.max()`, `.regex()`, `.email()`, `.uuid()`, `.datetime()` and the other checks

These **are** transforms (Zod 4 models `.transform()` as a pipe whose output is a transform node, which is what the walk looks for):

- `.transform(fn)` anywhere, including inside `z.array(...)`, `z.record(...)`, union members, and intersection branches
- `.pipe(...)` where the receiving end transforms
- `z.coerce.number()`, `z.coerce.date()` and friends — coercion is a transform with nicer syntax

### If the transform really is the output shape

If you were transforming to describe what your function *returns*, put the transformed shape in `output` and drop the transform:

```typescript
// ✅ Correct — output describes what the client receives, no transform needed
export const AssessmentOutput = z.object({
  id: z.string(),
  scheduledAt: z.date(),
})
```

## Schema Authoring Best Practices

- Treat `input`/`output` schemas as the wire contract: they must be statically analysable and serialisable to JSON Schema, because they're published to the OpenAPI document and the generated clients.
- Validate at the edge, convert in the function. A schema answers "is this well-formed?"; the function answers "what do I do with it?".
- Keep schemas in a dedicated `*.schemas.ts` file, exported as named variables — see [PKU489](./pku489.md) and [PKU490](./pku490.md).
- If you have a general-purpose Zod schema with transforms used elsewhere in your app, keep it, and derive a plain wire schema for Pikku rather than wiring the transforming one.

## Common Mistakes

- **`z.coerce.*` in an input schema.** It looks like a type, but it's a transform. Send the right type from the client instead.
- **Trimming or lowercasing in the schema.** `z.string().trim()` is a check and is fine; `.transform((s) => s.trim())` is not. Normalise inside the function for anything more involved.
- **Assuming only top-level transforms count.** The error path (`.user.email`, `.items[]`) tells you it found one nested — read the path before hunting through the whole file.
- **Reusing a domain schema that already had a transform.** The schema worked fine in your service layer; wiring it as `input` is what makes the transform a problem.
- **Only fixing the field the error names.** The check reports the *first* transform it finds. Fix it and re-run — a second one may be waiting behind it.
