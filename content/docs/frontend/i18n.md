# Internationalization

"Which language?" has a few different answers in a Pikku project, and they live
in different places. This page walks through all of them: what you author in
code, what the frontend renders, how the active locale gets picked, and the
tooling that stops you shipping an untranslated string.

## The big picture

| Layer | What it covers | Where it lives |
| --- | --- | --- |
| **Identifiers** | Function, component, type and file names; database tables and columns | Always English. Nothing changes this |
| **Meta** | `description`, `name`, `title` and step templates you author in backend code | `metaLocale` in `pikku.config.json` |
| **Product UI** | Every string a user sees in your app | `messages/<locale>.json`, compiled by [Paraglide JS](https://inlang.com/m/gerre34r/library-inlang-paraglideJs) |
| **Locale selection** | Which locale is active, how it's remembered, which way text flows | `createLocaleStore` from `@pikku/react` |
| **Enum labels** | Human labels for closed sets (statuses, roles, kinds) | `enum__*` message keys + `@pikku/paraglide` |
| **Email** | Per-locale strings for email templates | `locales/<locale>.json` inside `emailTemplatesDir` |
| **Checks** | Catching hardcoded copy and bad config | TypeScript, the i18n-debug mask locale, `pikku` config validation, the Fabric validator |

"The whole product is German" is a statement about the product, not the
codebase. You can run a fully German app with English identifiers, English
`baseLocale`, and German messages. Keeping those axes separate is what makes
adding a language later a file drop instead of a rewrite.

Every package named here is plain tooling you opt into. The core runtime has no
opinion on your UI language.

## Meta: `metaLocale`

`metaLocale` in `pikku.config.json` is the language tag for the meta you write
in code: function and step `description`s, feature and scenario `name`/`title`,
step `template` strings, role and persona descriptions.

| Key | Type | Default | Notes |
| --- | --- | --- | --- |
| `metaLocale` | `string` | `"en"` | A BCP-47 tag such as `en`, `de`, `pt-BR` |

How the CLI treats it:

- The value is canonicalised, so `EN-gb` and `en-GB` end up as the same thing.
- Use a hyphen, not an underscore. `de_DE` fails config loading with an error
  explaining the BCP-47 form.
- A non-string value fails the same way.
- The old spelling `locale` is rejected with an error telling you to rename it
  to `metaLocale`. The value is unchanged.
- It never renames anything. A German `metaLocale` buys you German
  descriptions, not a `getUebersicht` function.
- It is not the language your app speaks to users. That's the product UI
  setting below.
- Right now nothing reads it back: setting it records the language of your
  authored meta and validates the tag, but it doesn't change what any tool
  renders yet.

See [CLI configuration](/docs/pikku-cli/configuration) for the full key list.

## Product UI: messages

Every visible string in a Pikku frontend is a message. Messages live in
`messages/<locale>.json` (inlang message format), and Paraglide compiles them
into typed functions under a namespace usually imported as `m`. An app that
ships only English still does this — the messages are the seam a second
language slots into later, and a typo is a type error rather than a runtime
surprise.

The rules:

- Fixed copy is a message: add the key to `messages/en.json`, then call
  `m.<key>()`.
- A label with a variable is a **parameterized message** with a `{name}`
  placeholder in the catalogue and the value passed as an argument. Don't
  concatenate English around a runtime value.
- `asI18n(value)` is for opaque server data only (a name, a slug, an id, a
  formatted number). Never wrap a hardcoded English string in it. It's exported
  from `@pikku/react` along with the `I18nString` and `I18nNode` types.
- Message names are compile-time symbols. Don't build a key at runtime
  (`m['x_' + y]()`): a computed key can't be type-checked or tree-shaken, so a
  renamed message turns into silent runtime text. Map the discriminant to a
  message *function* instead. Enum labels (below) do exactly that for you.


### The gate

`I18nString` is structurally the same brand as Paraglide's `LocalizedString`, so
a compiled `m.key()` satisfies it with no wrapper. `I18nNode` is a drop-in for
`ReactNode` that allows everything except a bare `string`. The
[`@pikku/mantine`](/docs/frontend/react) components use it on their text props, so a raw
string literal on a gated prop is a compile error. `asI18n` is the deliberate
escape hatch.

The gate cannot see a hardcoded string in plain JSX, an `aria-label`, an `alt`,
or `document.title`. That's what the mask locale is for (see below).

### Project settings

Paraglide reads `project.inlang/settings.json`:

| Key | What it does |
| --- | --- |
| `baseLocale` | The message *source* catalogue every other locale is derived from. Keep it `en` |
| `locales` | Every locale that gets compiled |
| `modules` / `plugin.inlang.messageFormat.pathPattern` | Where the catalogues are read from, usually `./messages/{locale}.json` |

`baseLocale` is not the language your app speaks. Pointing it at `de` because
the product is German leaves you with no English catalogue to add another
language from, and repointing it later means re-keying everything. The Fabric
validator warns when an app's `baseLocale` isn't `en`. Set the language the app
opens in via `defaultLocale` instead (next section).

In the online-shop template, a Vite plugin (`paraglideVitePlugin`) compiles
`messages/*.json` into `src/paraglide` with HMR, and the app keeps an
`src/i18n/active.json` holding its `defaultLocale`. Fabric projects can change
it with the Fabric tool's `fabric i18n` command (it ships with Fabric, not
with the `pikku` CLI): `fabric i18n --default-locale <lang>` writes
`active.json`, and `fabric i18n --add-locale <lang>` adds the language to
`locales` and seeds `messages/<lang>.json` from `en.json`.

## Adding a language

1. Create `messages/<locale>.json` with the same keys as `messages/en.json`.
2. Add the locale to `locales` in `project.inlang/settings.json`.
3. Add it to `locales` in your `createLocaleStore` call.
4. Set `defaultLocale` there (or in your `active.json`) if it should be the
   language a new visitor lands in.
5. Recompile. The Vite plugin does this on save; otherwise run
   `paraglide-js compile`.

Email templates have their own catalogues — see [Emails](#emails).

## Choosing and switching the locale

`createLocaleStore` from `@pikku/react` is the reactive store behind the
messages. Your app supplies the locale list, a storage key and, optionally, a
startup policy. It hands back a set of functions:

| Return | What it does |
| --- | --- |
| `useLocale()` | React hook returning `{ locale, dir, setLocale }`. Subscribes the component so messages re-render on switch, no reload |
| `getLocale()` | The active locale, for date and number formatting |
| `setActiveLocale(l)` | The user chose a locale: switches and persists it |
| `setRouteLocale(l)` | The URL said so: switches but does *not* persist |
| `localeDir(locale?)` | `'ltr'` or `'rtl'` for a locale |
| `toLocale(value)` | Narrows an arbitrary string (a route param) to a supported locale, falling back to `defaultLocale` |
| `subscribe(listener)` | Raw subscription for non-React code |
| `isI18nDebug()` | Whether the mask locale is on |

```typescript @snippet create-locale-store
```

### Options

| Option | Required | Default | What it does |
| --- | --- | --- | --- |
| `locales` | yes | — | Every locale the app serves |
| `defaultLocale` | yes | — | Used when nothing else resolves |
| `storageKey` | no | none | `localStorage` key for the chosen locale. Omit it and the choice lasts for the session only |
| `overwriteGetLocale` | no | none | Paraglide's `overwriteGetLocale`, imported from *your* compiled runtime and passed in |
| `debugLocale` | no | none | The pseudo-locale code for i18n-debug mode |
| `rtlLanguages` | no | `ar`, `he`, `fa`, `ur` | Language codes that render right-to-left |
| `detectInitialLocale` | no | see below | Replaces the startup policy |

`overwriteGetLocale` is the one that bites. Every compiled message calls
Paraglide's own `getLocale()`, which on its own resolves through Paraglide's
cookie and URL strategies and knows nothing about your store. Without the
bridge, `m.foo()` renders one locale while your app believes in another. Pikku
never imports your compiled runtime itself, so you pass the function in.

### Startup order

Unless you pass `detectInitialLocale`, the first locale is the first of these
that matches a supported locale:

1. The persisted choice under `storageKey`
2. The browser language (`navigator.language`)
3. The `lang` attribute on `<html>`
4. `defaultLocale`

On the server there's no `window`, so the answer is `defaultLocale`.

Matching is on the first two letters, lowercased. `pt-BR` and `de-AT` match
`pt` and `de`. Region-specific catalogues like `pt-BR` as a separate locale are
not matched by this default policy. If your app resolves locale from somewhere
else (the route, the signed-in user), pass `detectInitialLocale`; it receives
`normalize` and `defaultLocale`.

### Fallbacks, summarised

- Unknown or unsupported tag: `normalize` gives `undefined`, and the startup
  order moves to the next source, ending at `defaultLocale`.
- `toLocale` on a bad route param: `defaultLocale`.
- A persisted locale that has since been removed from `locales`: ignored, next
  source wins.

### `lang` and `dir`

The store sets `<html lang>` and `<html dir>` at creation and on every change.
That matters for hydration: the server renders the base locale because it can't
see `localStorage`, and React doesn't patch mismatched attributes on hydrate,
so setting them at startup is what keeps a persisted RTL locale from coming
back as right-to-left text in a left-to-right layout.

## RTL

Direction is one setting. The store computes `dir` from the active locale and
writes it on the document root; the browser, and Mantine, mirror everything.
It only works cleanly if every custom style is flow-relative: `margin-inline-start`,
`text-align: start`, Mantine's `ms`/`me`, not `margin-left`, `text-align: left`
or `ml`/`mr`. Write logical properties from day one, even in an English-only
app, and Arabic, Hebrew, Farsi or Urdu are just another catalogue.

## Enum labels

An enum, status, kind or role is a closed set, so its label is a static map
entry, never a dynamic lookup. Put the labels in the catalogue under the
reserved `enum__<group>__<member>` namespace:

| Part | Rule |
| --- | --- |
| `enum` | Default prefix (option `prefix`) |
| `__` | Default separator between prefix, group and member (option `separator`). A single `_` joins words inside a segment |
| Example | `enum__booking_status__form_received` is the `form_received` member of the `booking_status` group |

`@pikku/paraglide` reads the catalogue and generates `i18n-enum.gen.ts`. For
each group it exports a map keyed by the member, with one message accessor per
member, exported under the group's camelCase name (`bookingStatus`). You call
the accessor at render time (`bookingStatus[value]()`) so the label follows the
active locale. The file is generated: don't edit it.

```typescript @snippet enum-label-lookup
```

Two guarantees come from types alone:

- Add an enum member without a catalogue key, or delete a key, and `tsc` fails.
- The map is exhaustive over the member union.

For a value that can be anything the server sends, check membership first and
fall back to `asI18n(value)`.

Members have to be valid JavaScript identifiers. Spell out leading digits
(`two_guests`, not `2_guests`); the generator quotes bad names as a fallback but
warns you to rename.

### Reconciling with the database

The database is the source of truth for what an enum can be. Point the
generator at the CLI's generated `enums.gen.ts` (Postgres native enums and
SQLite `CHECK (col IN (...))` constraints both produce one) and:

| Situation | Result |
| --- | --- |
| A catalogue group whose members **exactly match** a DB enum | The map is typed against that DB enum, so a dropped member or missing key fails `tsc` |
| A DB enum with **no** catalogue group | By default a map is generated that references `enum__<table>_<column>__<member>` keys, so `tsc` tells you which to add. Set `unmatchedDbEnums: 'warn'` to only report it |
| A catalogue group with a member the DB doesn't have | A drift warning suggesting you make it a standalone message instead of an enum member |

An enum label you never render costs nothing: Paraglide only compiles the
messages actually referenced.

### Running the generator

Vite (recommended): `paraglideEnums` from `@pikku/paraglide/vite`. Put it
**after** `paraglideVitePlugin`, because the generated file imports the
compiled `m`. It regenerates on catalogue edits in dev and only writes when the
output changes, so it never loops HMR.

| Option | Default | What it does |
| --- | --- | --- |
| `catalog` | `./messages/en.json` | Base-locale catalogue to read |
| `outFile` | `./src/i18n/i18n-enum.gen.ts` | Generated module |
| `enumsFile` | none | The CLI's generated `enums.gen.ts` to reconcile against (usually under `.pikku/db/`) |
| `enumsImport` | relative path from `outFile` to `enumsFile` | Specifier the generated file uses to import the DB types. Set it to use a package mapping |
| `messagesImport` | `./messages.js` | Where the generated file imports your wrapped `m` from |
| `i18nImport` | `@pikku/react` | Where `I18nString` comes from |
| `prefix` / `separator` | `enum` / `__` | The reserved namespace |
| `unmatchedDbEnums` | `emit` | `emit` or `warn` |

```typescript @snippet paraglide-enums-vite-config
```

For CI or non-Vite flows, run the `paraglide-enums` binary right after
`paraglide-js compile`:

```bash
paraglide-enums <catalog.json> <out.gen.ts> [messagesImport] [enums.gen.ts]

paraglide-enums ./messages/en.json ./src/i18n/i18n-enum.gen.ts ./messages.js ./packages/functions/.pikku/db/enums.gen.ts
```

It exits non-zero if the arguments are missing or the catalogue isn't found.

## Finding hardcoded strings: the i18n-debug mask

The mask renders every message as block glyphs, so whatever you can still read
on screen never went through a message.

```text
████ ███████        <- a message
Save changes         <- a hardcoded string
```

It's implemented as a pseudo-locale, not a runtime wrapper, so Paraglide keeps
tree-shaking unused messages. `{placeholders}` and whitespace are left alone, so
masked text keeps the shape of the original and layout bugs still look like
layout bugs.

Setup is three pieces:

1. `paraglideMaskLocale` from `@pikku/paraglide/vite`, placed **before**
   `paraglideVitePlugin`. It writes the masked catalogue beside the base one.
2. `debugLocale: 'zz'` (or whatever code you chose) on `createLocaleStore`.
3. Keep that code **out** of your app's supported `locales` list. That list
   drives URL prefixes, hreflang and any backend `locale` param, none of which
   should see it.

| `paraglideMaskLocale` option | Default |
| --- | --- |
| `catalog` | `./messages/en.json` |
| `locale` | `zz` |
| `outFile` | `<locale>.json` next to the catalogue |

In dev it rewrites the mask whenever the base catalogue changes. A stale mask
shows a new message as readable text, which is indistinguishable from the bug
you're hunting. On a production build the file is deleted instead of written,
and Paraglide compiles the locale to aliases of the base locale, so shipping it
costs effectively nothing.

Turning it on in the browser (any one of these):

| Toggle | Effect |
| --- | --- |
| `?i18n-debug` in the URL | On. `?i18n-debug=0` turns it off |
| `localStorage['i18n-debug'] = '1'` | On |
| `I18N_DEBUG=1` environment variable | On (server rendering) |

The answer is read once and cached, since it's checked on every message call.
Reload after changing the localStorage flag.

The package also exports `maskCatalog` and `maskMessage` if you want to build
the masked catalogue yourself.

## Emails

Email templates carry their own locale catalogues, separate from the UI
messages. They live in `locales/<locale>.json` inside `emailTemplatesDir`.
`pikku emails init` scaffolds an `en` and a `de` catalogue; `pikku emails
generate` reads every file in that folder and generates typed renderers. The
generated `EmailLocale` type is the union of the catalogue file names, and a
template reference takes an optional `locale`.

```bash
pikku emails init
pikku emails generate
```

See [Email service](/docs/api/email-service) for sending.

## Checks that protect you

| Check | What it catches |
| --- | --- |
| TypeScript | A missing or renamed message key; a dropped enum member; a bare string on an `I18nNode` prop |
| `pikku` config loading | A malformed `metaLocale`; the old `locale` key |
| Mask locale | Hardcoded copy in plain JSX, `aria-label`, `alt`, `document.title` |
| Fabric validator | An app whose `baseLocale` isn't `en`; browser-test steps that locate elements by literal copy that also exists in the base catalogue, since a copy edit then breaks the test as a timeout rather than a clear failure |

For scenario steps, locate by the message key's value from the catalogue rather
than a copied literal.

## What not to do

- **Don't resolve a message key at runtime.** No `m['enum__' + x]()`, no
  key-string helper. Map to a message function.
- **Don't `asI18n()` a hardcoded English string.** Fixed copy is `m.<key>()`; an
  enum value goes through its generated label map.
- **Don't set `baseLocale` to your product's language.** It names the message
  source and stays `en`.
- **Don't add the mask locale to `locales`.**
- **Don't import another app's generated Paraglide runtime into a shared
  package.** Pass `overwriteGetLocale` in from the app instead.
